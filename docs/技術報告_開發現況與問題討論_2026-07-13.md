## 1. 背景與目標

現有系統以 ORP（氧化還原電位）訊號預測生物反應器的 CH4 產出，過去的離線分析只取「每個排氣週期一個 CH4 峰值」當標籤，樣本量僅 n=6，統計可信度低。本次開發的核心目標是把 CH4 資料從「每週期一個標量」升級為「每分鐘連續記錄」，並同步整備 x86 監控電腦與 Jetson Orin Nano 的雙環境驗證基礎設施。硬體端已同步改成每分鐘排氣偵測（原本約 7-8 天一次），2026-07-13 正式上線，屆時將開始累積新規格資料。

### 2.2 每分鐘連續分析管線

在既有的 cycle-level（週期級）分析之外，新增了 minute-level（分鐘級）分析管線，兩者的技術差異：

**特徵計算改用「連續區段」而非「週期」為單位。** 原本的做法是每個週期各自重跑一次 ORP 的 EMA（指數移動平均）/斜率/MACD 計算，這會在每個週期開頭產生 EMA 冷啟動失真（EMA 需要一段暖機期才能收斂到穩定值，每次重新從頭算，週期邊界附近的數值會失真）。新做法先依時間斷點（如斷線重啟造成的資料缺口）切出連續區段，在整個區段上連續計算，只在週期邊界處切標籤，數值本身不受週期切分影響。

**交叉驗證方法改變。** 樣本量從 n=6 暴增到 n=58,490 後，原本的 LOO-CV（留一法交叉驗證）不再適用，原因有二：(1) 逐分鐘資料高度自相關，LOO-CV 讓相鄰分鐘同時出現在訓練集與測試集，等於洩漏資訊；(2) 學術文獻（Austin et al., 2025, *Science Advances*）指出 LOO-CV 在正則化模型（如 Ridge）與小樣本情境下存在「分布偏誤」，會系統性低估真實誤差。改用：
- **GroupKFold**：以週期（cycle_id）為分組單位，同一週期的所有分鐘只會出現在同一折，模擬「對完全沒看過的週期做預測」的真實情境。
- **時序 holdout**：依日期切分，訓練用較早的資料、驗證用較晚的資料，模擬實際部署時「用歷史資料訓練、預測未來」的情境，也是回應學界對 LOO-CV 分布偏誤疑慮的具體作法。

**結果對照**：

| | 樣本數 | Ridge RMSE | RF RMSE |
|---|---|---|---|
| Cycle-level（LOO-CV） | 6 | 3.13% | 10.17% |
| Minute-level（GroupKFold） | 58,490 | 4.26% | **2.28%** |
| Minute-level（時序 holdout） | 58,490 | 4.42% | **1.72%** |

## 3. 目前面臨的問題、提出的解決方向與技術原理

### 3.1 問題：ORP 對 CH4 的邊際貢獻，目前樣本數估計得不夠精確

**現象**：`non_orp_baseline`（不用 ORP）的 RF RMSE 是 2.93%，跟主結果 2.28% 差距不大，看起來 ORP 貢獻有限。但把 GroupKFold 的 6 折拆開來看（逐折配對比較），6 折中有 5 折顯示「有 ORP」表現更好，差異平均 +0.53 個百分點；然而主結果自己的逐折 RMSE 就從 1.49% 跳到 3.03%（標準差 0.58），跟「有無 ORP」的平均差異是同一個數量級。

**技術原理**：這是典型的小樣本統計檢定力不足問題。GroupKFold 在 6 個週期上等同於留一週期法（leave-one-cycle-out），每一折的表現高度依賴「被留出的那個週期剛好長什麼樣子」，單一不尋常的週期就能大幅影響整體估計的變異數。要精確估計一個效應量（ORP 的邊際貢獻），需要的獨立樣本數遠比 6 多。

**解決方向**：不是靠更換分析方法解決，而是靠**累積更多獨立週期**（新硬體每分鐘排氣偵測上線後，理論上週期數會大幅增加，因為排氣頻率從每 7-8 天一次變成每分鐘偵測一次——但需注意這改變的是「取樣頻率」還是「真實生化週期長度」，需要看新資料實際呈現的週期結構才能確認）。論文措辭建議從「ORP 相位動態決定 CH4」調整為「ORP 相位動態提供獨立於操作參數與週期進度的額外解釋力，但目前樣本數尚不足以精確量化效應大小」，誠實標註統計限制。

### 3.2 問題：PINN 物理約束該用 Gompertz 還是 Monod，兩者的科學前提不同

**技術原理 — PINN**：物理資訊神經網路的核心概念，是在標準的資料誤差損失之外，額外加入一項「預測值違反已知物理/生化方程式的程度」：

```
Loss = Loss_資料誤差(預測 vs 真實) + λ × Loss_物理違反程度(預測是否符合方程式)
```

物理違反程度的計算，通常透過自動微分（automatic differentiation）直接從神經網路的輸出對時間求導，代入目標方程式的殘差項。這麼做的好處是在資料稀疏的區域（例如你們目前樣本數有限的情況），模型不會產生違反生化常理的預測，能提升小樣本下的泛化能力。

**技術原理 — Modified Gompertz 模型**：

```
P(t) = P_max × exp( -exp( (R_max·e/P_max)×(λ-t) + 1 ) )
```

`P_max`＝最終累積產氣上限、`R_max`＝最大產氣速率、`λ`＝遲滯期長度。這是描述**批次（batch）** 沼氣測試中「累積產氣量隨時間變化」的經典 S 型曲線，核心假設是「一次性投料，產氣先加速、再減速、最終打平」。

**技術原理 — Monod 方程式**：

```
μ = μ_max × S / (K_s + S)
```

`μ`＝比生長速率、`S`＝限制性受質濃度、`K_s`＝半飽和常數。這是描述微生物生長速率跟受質濃度關係的方程式，**天生為連續培養系統設計**（chemostat 理論的基礎），在厭氧消化模型中常被延伸用來描述產甲烷菌的受質消耗動態。

**問題所在**：你們的反應器是連續進料、週期性排氣運作，不是一次性投料的批次系統，沒有「最終打平」這件事，系統會不斷循環。Gompertz 的核心假設與實際系統不完全對齊；Monod 在概念上更貼近連續系統，但需要額外估計 `K_s`、`μ_max` 等動力學參數，通常需要受質消耗曲線的實驗資料才能擬合，目前不確定手上資料是否足夠。

**待解決**：這是生化機制判斷問題，不是工程問題，需要洪博的專業意見來確認：(1) 是否採用 PINN 這個方向，(2) 若採用，Gompertz、Monod 或其他動力學模型哪個更適合這個系統的實際運作模式。

### 3.3 問題：Bi-LSTM 存在即時推論的架構性限制

**技術原理**：現有 `core/model.py` 的 LSTM 是單向的，只能利用過去的資訊預測未來，這是刻意設計——因為它要在線上即時運作，物理上不可能取得未來時間點的資料。Bi-LSTM（雙向 LSTM）則是同時執行兩條 LSTM：一條正向讀取（過去→未來）、一條反向讀取（未來→過去），在序列中每一個時間點的表示法融合了兩個方向的資訊。

問題在於：反向 LSTM 要能運作，必須先取得該時間點之後的完整序列。這代表 Bi-LSTM **原理上無法用於真正即時的線上預測**——除非額外接受一段固定延遲（例如系統永遠比真實時間慢 N 分鐘再輸出，用這 N 分鐘的「未來」資料跑反向路徑）。

**解決方向**：若採用 Bi-LSTM，建議明確定位為**離線分析／可解釋性工具**（分析已發生的完整週期資料，找出 ORP 動態與 CH4 產出的深層關聯），或設計成固定延遲的準即時系統，兩種定位對工程實作的要求差異很大，需要在會議上明確拍板。

### 3.4 問題：Jetson 邊緣加速的套件生態斷層與系統限制

**技術原理 — 為什麼 Jetson 上裝不到官方 onnxruntime-gpu**：PyPI（Python 官方套件庫）上的 `onnxruntime-gpu` 只提供 x86_64 架構的預編譯二進位檔（wheel），Jetson 屬於 ARM64（aarch64）架構且搭載特定的 CUDA 運算能力版本（Orin 系列為 sm_87），這個組合的使用者規模遠小於 x86 伺服器市場，NVIDIA 並未透過標準 PyPI 通路發布對應版本，直接 `pip install onnxruntime-gpu` 在 Jetson 上完全裝不起來。

**已驗證的解決方案**：改用容器化分發——`dusty-nv/jetson-containers` 專案針對每個 JetPack/L4T 版本組合，預先編譯好完整環境（含正確版本的 CUDA、cuDNN、TensorRT、onnxruntime）並封裝成 Docker 映像，直接下載對應版本的映像即可繞過從源碼編譯的複雜度。已在 Jetson 上實測 `dustynv/onnxruntime:r36.2.0`（約 13GB），容器內確認 `TensorrtExecutionProvider`／`CUDAExecutionProvider` 皆正常可用。

**技術原理 — 額外發現的網路限制**：Docker 預設的 bridge 網路模式，需要透過 iptables 的 `raw` 表格設定封包過濾規則（`DOCKER-USER` 鏈的直通過濾機制）。Jetson 這顆客製化 kernel（`5.15.136-tegra`）並未編譯 `iptable_raw` 這個核心模組，導致容器網路初始化失敗。解法是啟動容器時加上 `--network host`，讓容器直接共用主機的網路命名空間，跳過 Docker 自建的 bridge 網路與相關 iptables 規則，此法已驗證有效。

### 3.5 問題：時程風險——原計畫 5-6 個月 vs 實際 7 週

**現況**：截稿 2026-08-31，今天起僅約 7 週。若採用完整範圍（Bi-LSTM + PINN + 雙環境部署 + TensorRT 量化 + 14 天影子測試），依照計畫，14 天的影子測試本身是日曆天限制，無法用加班壓縮，最晚必須在 8/17 前開始才能留出後續分析寫稿時間，這代表從現在到 8/17 的約 5 週內，要完成模型開發、訓練、部署整合。

**已降低的風險**：原本這塊評估中，Docker/ONNX/TensorRT 的環境建置是最大的不確定因素（可能卡關數天甚至更久），現在已經**實測驗證通過**，這部分的時程風險已大幅降低，剩下的主要是模型設計/訓練與整合工作本身需要的時間，較容易估計。
