**1. 與洪博討論：以壓力動態預測反應槽狀態之新實驗方法構想**

討論核心構想：相較於直接量測氣體濃度（受限於排氣管路型感測器只能在排氣當下量到離散快照），槽內**壓力**變化本身可作為連續訊號來源。CO2 相對 H2 更快溶入水/液相（隨菌相消耗，氣相 CO2 轉為液相並使 pH 下降），因此壓力的動態變化間接反映了氣體被消耗/溶解的情形；透過壓力預測模型回推，理論上可推知氣體溶入量，不需要直接連續量測氣體濃度本身。

討論中提出以下操作參數構想，作為後續實驗設計基準：
- 槽內壓力操作範圍暫定固定在 0.9～1.2（單位待確認，現場記錄範圍為 0.6～1.2），作為受控基準
- 氣體比例 H2:CO2 固定為 4:1（對應甲烷化反應 4H2 + CO2 → CH4 + 2H2O 之化學計量比）
- 上述固定值日後也可視為刻意變動的操作變因，用來觀察環境擾動下的系統反應，非僅是靜態設定

另提出新的預測目標設計：以 1 分鐘、5 分鐘、10 分鐘等不同短時間窗口，量測壓力（及 pH）的**斜率**變化，而非設定絕對數值的上下限去做預測——即模型要預測的是變化速率，而非閾值判斷。仍待確認的是：需要多長的觀測窗口，才能穩定量到有意義的斜率（現場筆記以圖示標註「花多久就可以測」，尚無明確答案）；pH 是否適用同一套斜率預測邏輯，目前僅列出待補的座標軸，尚未實際規劃。

此構想與現行 ORP 循環分析屬於互補關係（筆記註明「ORP、循環都可以用」），並非要取代現有 Ridge/GA/RF 管線，而是作為壓力/氣體關係另一條可並行探索的預測路徑，且此構想目前仍是概念討論階段，尚未進入實驗設計或程式實作。

**2. 監控電腦開發環境建置與問題排除**

本次於監控電腦（金工電腦）上建置專案執行環境，過程中排除數個問題：該電腦原先未安裝 Node.js，執行 `npm run dev` 時完全無法運作，改以 winget 安裝 Node.js LTS（v24.18.0）後解決，並確認安裝後須重新開啟終端機視窗，PATH 環境變數方能生效。PowerShell 執行 npm 系列指令時另出現「running scripts is disabled on this system」錯誤，屬於執行原則（Execution Policy）預設值阻擋 npm 的 `.ps1` 腳本殼層，以 `Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned` 排除，僅影響目前使用者帳號。

Python 端執行 `python main.py` 時出現 `ModuleNotFoundError: No module named 'paho'`，追查後確認 `requirements.txt` 未列全所需套件（缺少 `paho-mqtt`、`pyserial`，另 `requests` 套件為 `sensor_simulator.py` 既有相依但未被列入需求檔的既存問題），已補齊後重新安裝解決。

此外，`main.py` 啟動時於例外處理流程本身又觸發 `UnicodeEncodeError` 而導致整個服務啟動失敗，追查後確認原因為 Windows 主控台/重導向輸出預設使用系統 codepage（如 cp1252），無法編碼程式中既有的中文 `print` 訊息（如「[AI 核心]」、「[MQTT]」等），已於 `main.py` 起始處強制 stdout/stderr 改用 UTF-8 編碼解決。此問題屬於任何非互動式啟動情境（背景執行、服務排程、輸出重導向至記錄檔）皆會觸發的根本性問題，非單一次意外。

**3. 監控電腦部署工具開發**

為簡化監控電腦現場操作，新增 `start_backend.bat` 批次檔，雙擊即可啟動虛擬環境並執行 `main.py`，若虛擬環境不存在會列印建立步驟並暫停視窗，程式結束或發生錯誤時同樣暫停顯示訊息，避免現場人員因視窗一閃而過而看不到錯誤內容。

另因監控電腦上既有每日備份 CSV（`BTP_Sensor_log-YYYY-MM-DD.csv`）原先僅能透過網頁介面逐筆手動選檔匯入，新增 `batch_import_csv.py` 批次匯入腳本，可一次指向整個資料夾，逐檔呼叫既有 `/import_csv` API 端點，並沿用該端點原有之時間戳記去重邏輯，可重複執行而不會造成資料重複匯入。

前端 API 連線位址原寫死於程式碼中（`192.168.55.1`，即 Jetson 之固定 IP），改用 Vite 環境變數區分：`.env.development` 對應本機開發（localhost），`.env.production` 對應監控電腦正式部署建置（連接 Jetson），已實際執行 `npm run build` 驗證打包結果正確寫入 Jetson IP，且與開發模式互不干擾。另將前端輪詢間隔自測試殘留值 5 秒改回設計值 60 秒，對應 USB 感測器每分鐘寫入一筆資料之實際頻率。

**4. Jetson 網路連線與 Git 同步機制建立**

Jetson Orin Nano 原僅能透過 Type-C 連接電腦、走 USB 網路共享方式取得固定 IP（`192.168.55.1`）與外部通訊，本次改連接現場 WiFi。過程中以 `nmcli device wifi connect` 一行式指令連線時出現 `Error: invalid extra argument 'password'`，改以 `nmcli connection add` / `modify` / `up` 三段式指令排除，已確認連線成功。

同時建立「本機開發 → `git push` → 監控電腦／Jetson 各自 `git pull`」三方同步流程：Jetson 端因 SSH 非互動式連線缺乏憑證，`git push` 目前無法執行，惟此流程僅需 Jetson 端執行 `git pull`，不受此限制影響。本次已推送 3 個 commit 至遠端主分支，內容涵蓋開發環境修復、文件更新、`start_backend.bat` 新增。

**5. 即時運算架構盤點與規劃**

討論確認系統架構方向：監控電腦負責感測器資料收集與前端顯示，實際 LSTM 推論運算交由 Jetson 執行，運算結果透過 MQTT 發布，前端訂閱顯示。盤點既有程式碼後確認此架構已有相當程度之既有實作：`core/mqtt_client.py` 已設計為運行於 Jetson（Broker IP 設定為 `localhost` 並附註明「因為 Broker 就裝在 Jetson 上」），訂閱 `reactor/01/sensors` 主題、收到資料後呼叫既有推論函式、將結果發布至 `reactor/01/prediction` 主題；前端 `MonitorView.vue` 亦已訂閱該預測結果主題並自動更新畫面。

現有缺口在於：實體 USB 感測器僅接於監控電腦，惟 `usb_receiver.py` 收到資料後僅寫入本機資料庫與 CSV 備份，未自動轉發至 MQTT（現行僅前端手動點擊「發布」按鈕可單筆送出）。此部分待確認 Jetson 端是否已安裝並啟動 MQTT Broker（如 Mosquitto）後，即可著手修改 `usb_receiver.py` 補上自動轉發邏輯。
