# Bi-LSTM / 邊緣加速路線評估

**用途**：2026-07-13 與洪博討論「要不要走 Bi-LSTM + PINN + 邊緣加速（ONNX/TensorRT/Docker）這條線」的決策依據
**前提**：截稿 2026-08-31，今天 2026-07-11 起僅約 7 週

---

- **7/13 部署順序已定案**：先在金工電腦＋Jetson 兩邊裝好「原始系統」（現有 Ridge/GA/RF pipeline，不含 Bi-LSTM/ONNX），開始收集新硬體（每分鐘排氣偵測）產生的資料。Docker、ONNX、Bi-LSTM 全部歸類為「後續再做」，不卡在 7/13 這關，部署步驟見〈[金工電腦部署清單_2026-07-13.md](金工電腦部署清單_2026-07-13.md)〉。

---

## 2. 提案內容摘要

外部（AI 生成）研究計畫書提議的範圍：
1. 演算法從 Ridge/GA 升級為 **Bi-LSTM**（雙向 LSTM）或結合注意力機制，甚至整合 **PINN**（物理資訊神經網路，把 Gompertz/Monod 動力學方程式嵌入 loss function）。
2. **雙環境（金工電腦 + Jetson）同步驗證**：兩邊跑一樣的模型，比較延遲/精度/資源消耗。
3. Jetson 端用 **ONNX Runtime + TensorRT** 做邊緣加速與量化（FP16/INT8）。
4. 用 **Docker 多架構容器**保證兩邊軟體環境一致。
5. 原計畫時程：5-6 個月。**實際只有 7 週**，時程風險已在前份文件中詳細拆解。

## 3. 今天做的可行性驗證（實測證據，非猜測）

| 驗證項目 | 結果 |
|---|---|
| ONNX 匯出（x86，`ReactorLSTM`） | ✅ 成功。PyTorch vs ONNX Runtime 輸出誤差 1.49×10⁻⁸（數值等價），動態 batch 驗證通過。過程踩到 3 個依賴地雷（`onnx`/`onnxruntime`/`onnxscript` 皆未安裝，opset 版本需 fallback 轉換），但都能快速排除。已寫成可重用腳本 `edge_backend/export_onnx.py`。 |
| Jetson 現況（SSH 確認） | JetPack 6.x（L4T R36.3.0），已有 NVIDIA 官方 CUDA 版 PyTorch (`2.4.0a0+...nv24.5`)、numpy/pandas/scikit-learn。 |
| Jetson 端 `onnxruntime-gpu` 官方安裝路徑 | ❌ **PyPI 上沒有 aarch64+CUDA(sm_87) 的官方預編譯 wheel**，直接 `pip install onnxruntime-gpu` 行不通。 |
| 替代方案：`jetson-containers`（dusty-nv） | ✅✅ **已在 Jetson 實機完整驗證成功**（不只是查證，是真的拉下來跑過）：`docker pull dustynv/onnxruntime:r36.2.0`（約 13GB，下載約需 20-30 分鐘），容器內 `onnxruntime 1.16.3`，`get_available_providers()` 回傳 `['TensorrtExecutionProvider', 'CUDAExecutionProvider', 'CPUExecutionProvider']`——**TensorRT 與 CUDA 加速引擎都確認可用**。這個地雷已經徹底解決。 |
| x86 監控電腦 Docker | ✅ Docker Desktop（WSL2 backend）已裝好並實測：`edge_backend/Dockerfile` build 成功，容器內完整安裝 requirements.txt（含 onnx/onnxruntime/onnxscript），`loader.py`/`main.py` import 正常。不含 USB 裝置直通（需另裝 `usbipd-win`）。 |
| Jetson 執行容器的額外限制 | Jetson 這顆客製化 kernel（`5.15.136-tegra`）缺少 `iptable_raw` 模組，Docker 預設 bridge 網路建不起來，需加 `--network host` 繞過；GPU 容器需加 `--runtime nvidia`。這兩個旗標已確認有效，記錄下來供之後複用。 |

**結論**：Bi-LSTM 的邊緣部署技術路徑**已經端到端驗證過，不再是理論可行，是實測可行**——x86 端 Docker、Jetson 端 `jetson-containers`（含 TensorRT/CUDA）都已經跑起來過。剩下真正的不確定性只在第 4 節那些需要洪博判斷的科學/範圍問題，不再是「能不能做」，而是「值不值得在 7 週內做」。

## 4. 需要跟洪博一起拍板的決策題

1. **要不要做**：現有 Ridge/GA/RF 結果（含消融實驗）是否已足以支撐這次投稿？Bi-LSTM/PINN/邊緣加速是否列為這次投稿的必要項目，還是留給下一篇論文？
2. **PINN 的科學前提**：Modified Gompertz 模型是批次式沼氣測試的經典模型，本反應器是連續進料運作，兩者數學前提是否對齊？這是生化機制問題，需要洪博的專業判斷，不是我能確認的。
3. **範圍怎麼切**：如果要做，是做到「Bi-LSTM 訓練 + 離線分析」就好，還是要做完整的「Jetson 邊緣部署 + TensorRT 量化 + 14 天影子測試」？後者時程壓力大很多。
4. **Bi-LSTM 的即時推論限制**：雙向 LSTM 需要看到「未來」的時間步，無法直接用於即時線上預測（現有 `core/model.py` 用單向 LSTM正是因為要即時運作）。如果要做 Bi-LSTM，它的定位會是離線分析／解釋工具，還是要設計成固定延遲窗口的準即時系統？這會影響工程量。
5. **時程紅線**：14 天影子測試最晚要 8/17 前開始（見前份文件的日曆試算），若採用完整範圍，5 週內要把 Docker/jetson-containers/ONNX/TensorRT 全部建置到能穩定跑 14 天不出包，這件事本身有沒有把握做到，需要現在誠實評估。

## 5. 建議的分階段作法（不管決策為何都適用）

無論 7/13 決定要不要做 Bi-LSTM，建議的執行順序都一樣，差別只在做到哪一步就停：

```
第 0 步（已完成）：Ridge/GA/RF 管線驗證 + 消融實驗
第 0.5 步（已完成，提前做掉了）：x86 Docker + Jetson jetson-containers
    （TensorRT/CUDA onnxruntime）端到端驗證成功
第 1 步（7/13 開始）：兩邊機器部署「原始系統」，開始收集新硬體資料
    ↓
── 若決定不做 Bi-LSTM，到此為止，全力投入資料分析與論文寫作 ──
    ↓
第 2 步（若決定要做）：Bi-LSTM 模型設計與離線訓練（用累積中的新資料）
第 3 步：視時間餘裕決定要不要正式做 TensorRT 量化 + 雙環境影子測試
    （基礎設施已就緒，這步主要是模型訓練與實際部署整合的時間投入）
```

這樣設計的用意：**每一步都是前一步驗證通過才往下走，不會因為後面的步驟卡關而拖累前面已經有把握的部分**。
