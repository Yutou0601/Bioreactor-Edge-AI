# CH4 每分鐘連續記錄系統：開發現況、技術原理與問題討論

**整理日期**：2026-07-12（供 2026-07-13 與洪博討論用）
**投稿目標**：ACM ICEA 2026，截稿 2026-08-31

## 1. 背景與目標

現有系統以 ORP（氧化還原電位）訊號預測生物反應器的 CH4 產出，過去的離線分析只取「每個排氣週期一個 CH4 峰值」當標籤，樣本量僅 n=6，統計可信度低。本次開發的核心目標是把 CH4 資料從「每週期一個標量」升級為「每分鐘連續記錄」，並同步整備 x86 監控電腦與 Jetson Orin Nano 的雙環境驗證基礎設施。硬體端已同步改成每分鐘排氣偵測（原本約 7-8 天一次），2026-07-13 正式上線，屆時將開始累積新規格資料。

### 2.2 每分鐘連續分析管線

在既有的 cycle-level（週期級）分析之外，新增了 minute-level（分鐘級）分析管線，兩者的技術差異：

**特徵計算改用「連續區段」而非「週期」為單位。** 原本的做法是每個週期各自重跑一次 ORP 的 EMA（指數移動平均）/斜率/MACD 計算，這會在每個週期開頭產生 EMA 冷啟動失真（EMA 需要一段暖機期才能收斂到穩定值，每次重新從頭算，週期邊界附近的數值會失真）。新做法先依時間斷點（如斷線重啟造成的資料缺口）切出連續區段，在整個區段上連續計算，只在週期邊界處切標籤，數值本身不受週期切分影響。

**交叉驗證方法改變。** 樣本量從 n=6 暴增到 n=58,490 後，原本的 LOO-CV（留一法交叉驗證）不再適用，原因有二：(1) 逐分鐘資料高度自相關，LOO-CV 讓相鄰分鐘同時出現在訓練集與測試集，等於洩漏資訊；(2) 學術文獻（Austin et al., 2025, *Science Advances*）指出 LOO-CV 在正則化模型（如 Ridge）與小樣本情境下存在「分布偏誤」，會系統性低估真實誤差。改用：
- **GroupKFold**：以週期（cycle_id）為分組單位，同一週期的所有分鐘只會出現在同一折，模擬「對完全沒看過的週期做預測」的真實情境。
- **時序 holdout**：依日期切分，訓練用較早的資料、驗證用較晚的資料，模擬實際部署時「用歷史資料訓練、預測未來」的情境，也是回應學界對 LOO-CV 分布偏誤疑慮的具體作法。

**結果對照**：

| | 樣本數 | Ridge RMSE | RF RMSE |
|---|---|---|---|
| Cycle-level（LOO-CV） | 6 | 3.13% | 10.17% |
| Minute-level（GroupKFold） | 58,490 | 4.26% | **2.28%** |
| Minute-level（時序 holdout） | 58,490 | 4.42% | **1.72%** |

### 2.5 容器化基礎設施驗證

針對另一份外部研究計畫書提議的「Docker 多架構容器 + ONNX Runtime + TensorRT 邊緣加速」路線，做了端到端的技術可行性驗證（不是紙上談兵，是真的裝、真的跑）。以下先說明三項關鍵技術各自要解決什麼問題，再列出實際驗證結果。

**技術原理 — Dockerfile／容器化要解決的問題**：這條專案有兩台性質完全不同的機器——x86 監控電腦（開發與離線分析用）與 Jetson Orin Nano（ARM64 邊緣推論用），兩邊的作業系統、Python 版本、可用的套件 wheel 都不同。若靠手動安裝，很容易出現「我這邊跑得動、換一台就壞」的環境漂移問題（依賴版本、系統函式庫、CUDA 版本任一項不一致都可能出錯），且難以重現、難以在論文中交代實驗環境。Dockerfile 是容器映像的建置腳本，把「作業系統基底 + 系統套件 + Python 套件 + 專案程式碼」完整寫成可重複執行的步驟，`docker build` 之後產出的映像在任何裝有 Docker 的機器上都會得到位元組層級相同的執行環境。目前 `edge_backend/Dockerfile` 鎖定 `python:3.10-slim` 為基底映像，版本刻意對齊 Jetson 上實測到的 Python 3.10.12（見 2.4 節），縮小兩邊「語言層級」行為差異；再分兩步安裝依賴：先裝 CPU 版 PyTorch（`--index-url https://download.pytorch.org/whl/cpu`，因為 x86 監控電腦這條分析管線不需要 GPU，CPU 版體積小、下載快），再裝 `requirements.txt` 其餘套件。已知限制是 USB 感測器（`/dev/ttyUSB0`）在 Windows + Docker Desktop 環境下沒有原生裝置直通，`usb_receiver.py` 這條即時收資料的路徑目前不在容器化範圍內，僅涵蓋 API 服務與離線分析。此映像已實際 `build` 成功、容器內程式碼可正常載入執行。

**技術原理 — ONNX Runtime／onnxruntime-gpu 要解決的問題**：模型訓練通常用 PyTorch，但 PyTorch 是一個完整的訓練框架，體積大、啟動慢，且原生的 `.pt` 模型檔綁定 PyTorch 的執行環境，換一個裝置或程式語言不一定能直接載入。ONNX（Open Neural Network Exchange）是一種與框架無關的模型交換格式：訓練完成後把 PyTorch 模型「匯出」成 `.onnx` 檔，之後推論階段只需要一個輕量的推論引擎（ONNX Runtime）去讀取並執行這個檔案，不需要整套 PyTorch。這樣做要解決的問題有二：(1) 推論效能——ONNX Runtime 在載入模型時會做圖優化（如算子融合、常數折疊），比直接用 PyTorch 跑推論通常更快、記憶體占用更小，這對邊緣裝置的即時服務很重要；(2) 部署可攜性——同一份 `.onnx` 模型檔可以在 x86 開發機與 Jetson 邊緣裝置上用同一套推論程式碼載入執行，不需要為兩邊各寫一套推論邏輯。`onnxruntime-gpu` 是 ONNX Runtime 額外編譯了 GPU 加速後端的版本（對比純 CPU 版的 `onnxruntime`），這是能不能吃到 GPU 加速的關鍵套件，也是 3.4 節要討論的套件斷層問題的主角。

**技術原理 — CUDAExecutionProvider／TensorrtExecutionProvider 要解決的問題**：ONNX Runtime 本身不直接跟某一種硬體綁死，而是透過「Execution Provider（執行提供者）」這層抽象，把「讀取並執行 ONNX 計算圖」跟「實際在哪種硬體後端上運算」分開。同一份模型檔案，在初始化 `InferenceSession` 時指定不同的 provider 清單，就能在不同硬體上跑：`CPUExecutionProvider` 是永遠可用的後備選項（純 CPU 運算）；`CUDAExecutionProvider` 把運算指派到 NVIDIA GPU 上用 CUDA 核心執行，比 CPU 快，但每個算子（operator）是各自呼叫、彼此之間仍有一些排程與記憶體搬移開銷；`TensorrtExecutionProvider` 則更進一步，會把整個（或大部分）計算圖交給 NVIDIA TensorRT 做「圖層級」的優化與編譯，包括算子融合、精度校準（可選用 FP16/INT8 量化）、針對特定 GPU 架構產生最佳化的執行計畫，通常比單純的 CUDAExecutionProvider 更快，但初次載入需要花時間編譯，且對算子支援度較嚴格（不支援的算子會自動退回 CUDA 或 CPU）。這一層設計要解決的問題是：讓同一套推論程式碼、同一份模型檔案，能在「有無 GPU」「GPU 等級高低」「是否要用 TensorRT 量化」等不同部署情境下，透過設定切換就取得對應的最佳效能，不需要為每種硬體重寫程式。實務上會依照 provider 清單的優先順序依序嘗試，找不到就自動退回下一個，這也是為什麼 2.4／2.5 節會特別檢查容器內 `onnxruntime` 是否「同時具備」`TensorrtExecutionProvider` 與 `CUDAExecutionProvider`——這代表 GPU 加速路徑（無論走哪一層）確認可用。

驗證結果：

- **x86 監控電腦**：`edge_backend/Dockerfile` 已寫好並實際 build 成功，容器內完整安裝所有依賴套件，程式碼可正常載入。
- **Jetson 端**：確認官方 PyPI 沒有 aarch64+CUDA 架構的 `onnxruntime-gpu` 預編譯 wheel（這是這類邊緣裝置常見的套件生態斷層——見第 3.4 節技術說明），改用 `dusty-nv/jetson-containers` 專案提供的預建容器映像（`dustynv/onnxruntime:r36.2.0`），**已在 Jetson 實機拉取並驗證**：容器內 `onnxruntime` 同時具備 `TensorrtExecutionProvider` 與 `CUDAExecutionProvider`，代表 GPU 加速路徑確認可用。
- 過程中也確認並解決了 Jetson 客製化 kernel 特有的網路限制（見第 3.4 節）。

**目前與後續整合的關係**：以上驗證的是「基礎設施可用」，尚未把訓練好的模型接進這條管線——真正要用到 ONNX 匯出與 Execution Provider 切換，要等 2.6 節列出的 Bi-LSTM／PINN 等模型定案並訓練完成後，才會進入「PyTorch 模型 → 匯出 ONNX → Jetson 容器內用對應 Execution Provider 推論」這一步，屬於下一階段工作。

## 3. 目前面臨的問題、提出的解決方向與技術原理

### 3.1 問題：ORP 對 CH4 的邊際貢獻，目前樣本數估計得不夠精確

**現象**：`non_orp_baseline`（不用 ORP）的 RF RMSE 是 2.93%，跟主結果 2.28% 差距不大，看起來 ORP 貢獻有限。但把 GroupKFold 的 6 折拆開來看（逐折配對比較），6 折中有 5 折顯示「有 ORP」表現更好，差異平均 +0.53 個百分點；然而主結果自己的逐折 RMSE 就從 1.49% 跳到 3.03%（標準差 0.58），跟「有無 ORP」的平均差異是同一個數量級。

**技術原理**：這是典型的小樣本統計檢定力不足問題。GroupKFold 在 6 個週期上等同於留一週期法（leave-one-cycle-out），每一折的表現高度依賴「被留出的那個週期剛好長什麼樣子」，單一不尋常的週期就能大幅影響整體估計的變異數。要精確估計一個效應量（ORP 的邊際貢獻），需要的獨立樣本數遠比 6 多。

**解決方向**：不是靠更換分析方法解決，而是靠**累積更多獨立週期**（新硬體每分鐘排氣偵測上線後，理論上週期數會大幅增加，因為排氣頻率從每 7-8 天一次變成每分鐘偵測一次——但需注意這改變的是「取樣頻率」還是「真實生化週期長度」，需要看新資料實際呈現的週期結構才能確認）。論文措辭建議從「ORP 相位動態決定 CH4」調整為「ORP 相位動態提供獨立於操作參數與週期進度的額外解釋力，但目前樣本數尚不足以精確量化效應大小」，誠實標註統計限制。

### 3.2 問題：PINN 物理約束該用 Gompertz 還是 Monod，兩者的科學前提不同

**技術原理 — PINN**：物理資訊神經網路的核心概念，是在標準的資料誤差損失之外，額外加入一項「預測值違反已知物理/生化方程式的程度」：

```
Loss = Loss_資料誤差(預測 vs 真實) + λ × Loss_物理違反程度(預測是否符合方程式)
```

物理違反程度的計算，通常透過自動微分（automatic differentiation）直接從神經網路的輸出對時間求導，代入目標方程式的殘差項。這麼做的好處是在資料稀疏的區域（例如你們目前樣本數有限的情況），模型不會產生違反生化常理的預測，能提升小樣本下的泛化能力。

**技術原理 — Modified Gompertz 模型**：

```
P(t) = P_max × exp( -exp( (R_max·e/P_max)×(λ-t) + 1 ) )
```

`P_max`＝最終累積產氣上限、`R_max`＝最大產氣速率、`λ`＝遲滯期長度。這是描述**批次（batch）** 沼氣測試中「累積產氣量隨時間變化」的經典 S 型曲線，核心假設是「一次性投料，產氣先加速、再減速、最終打平」。

**技術原理 — Monod 方程式**：

```
μ = μ_max × S / (K_s + S)
```

`μ`＝比生長速率、`S`＝限制性受質濃度、`K_s`＝半飽和常數。這是描述微生物生長速率跟受質濃度關係的方程式，**天生為連續培養系統設計**（chemostat 理論的基礎），在厭氧消化模型中常被延伸用來描述產甲烷菌的受質消耗動態。

**問題所在**：你們的反應器是連續進料、週期性排氣運作，不是一次性投料的批次系統，沒有「最終打平」這件事，系統會不斷循環。Gompertz 的核心假設與實際系統不完全對齊；Monod 在概念上更貼近連續系統，但需要額外估計 `K_s`、`μ_max` 等動力學參數，通常需要受質消耗曲線的實驗資料才能擬合，目前不確定手上資料是否足夠。

**具體使用方式 — PINN 如何接進現有訓練管線**：實作上不需要換掉現有的神經網路架構，PINN 是一種訓練方式而非模型架構，可以直接套用在現有 LSTM 或未來的 Bi-LSTM 上，差異只在訓練迴圈本身：除了原本「預測 CH4 vs 真實 CH4」的資料誤差項，額外對模型輸出 P̂(t) 相對於時間 t 做自動微分（PyTorch 的 `torch.autograd.grad`，需要模型輸出與時間輸入之間保有計算圖），把微分結果代入選定方程式（Gompertz 或 Monod）的殘差形式，計算殘差平方作為物理損失項，兩者依 `Loss = Loss_資料 + λ × Loss_物理` 加權相加後反向傳播，一次更新即同時拉近「符合真實資料」與「符合方程式」兩個目標。實務上還需要決定「collocation points」——用來計算物理殘差的時間取樣點，可以直接沿用每分鐘資料的時間戳，不必額外取樣。權重 `λ` 的選擇會直接影響結果：太小則物理約束形同虛設、退化成一般 LSTM；太大則模型會為了滿足方程式殘差而犧牲擬合真實資料的準確度，通常需要用驗證集網格搜尋，或訓練前期先讓 `λ` 從 0 逐步調升（warm-up）來取得平衡。這件事在下方「待解決」的兩個問題定案（是否用 PINN、用哪個方程式）之前，都還停留在方法論層次，尚未動工。

**待解決**：這是生化機制判斷問題，不是工程問題，需要洪博的專業意見來確認：(1) 是否採用 PINN 這個方向，(2) 若採用，Gompertz、Monod 或其他動力學模型哪個更適合這個系統的實際運作模式。

### 3.3 問題：Bi-LSTM 存在即時推論的架構性限制

**技術原理**：現有 `core/model.py` 的 LSTM 是單向的，只能利用過去的資訊預測未來，這是刻意設計——因為它要在線上即時運作，物理上不可能取得未來時間點的資料。Bi-LSTM（雙向 LSTM）則是同時執行兩條 LSTM：一條正向讀取（過去→未來）、一條反向讀取（未來→過去），在序列中每一個時間點的表示法融合了兩個方向的資訊。

問題在於：反向 LSTM 要能運作，必須先取得該時間點之後的完整序列。這代表 Bi-LSTM **原理上無法用於真正即時的線上預測**——除非額外接受一段固定延遲（例如系統永遠比真實時間慢 N 分鐘再輸出，用這 N 分鐘的「未來」資料跑反向路徑）。

**解決方向**：若採用 Bi-LSTM，建議明確定位為**離線分析／可解釋性工具**（分析已發生的完整週期資料，找出 ORP 動態與 CH4 產出的深層關聯），或設計成固定延遲的準即時系統，兩種定位對工程實作的要求差異很大，需要在會議上明確拍板。

**具體使用方式 — 若定位為離線分析／可解釋性工具**：架構上把現有 `core/model.py` 的 `ReactorLSTM`（目前 `nn.LSTM(input_size, hidden_size, num_layers, batch_first=True)`，單向）改為 `bidirectional=True`，正反向輸出會在最後一維拼接，維度從 `hidden_size` 變成 `hidden_size*2`，對應的 `nn.Linear(hidden_size, output_size)` 輸入維度需同步調整為 `hidden_size*2`。訓練與分析資料只能用每分鐘連續管線（2.2 節）中已經完整結束的週期，因為反向 LSTM 需要整個週期的 ORP 序列才能運作，這天生排除「對進行中的週期即時預測」的用法。用途上，可以拿正反向隱藏狀態在時間軸上的變化，比對「只看過去」（現有單向 LSTM／Ridge/RF）與「看過完整週期」的預測差異，藉此定位「哪些時間點的 ORP 動態，需要靠未來資訊才能被準確解釋」——這對應到生化上「延遲效應」的存在與強度，可作為論文中討論 ORP 與 CH4 因果延遲的輔助分析工具，補充而非取代現有即時預測管線。

**具體使用方式 — 若定位為固定延遲準即時系統**：在服務端維護一個長度為 N 分鐘的滑動緩衝區，Bi-LSTM 只對「緩衝區起點」這個時間點做預測（此時它之後已經有 N 分鐘的真實資料可用來跑反向路徑），代價是系統輸出永遠比真實時間落後 N 分鐘。N 的選擇是精度與時效性的直接權衡：N 越大，反向路徑能看到越多未來資訊、預測理論上越準，但對「即時監控」的實用價值越低。這個 N 需要搭配 3.1 節提到的、新硬體資料上線後的週期結構重新評估——例如若排氣事件的生化前兆通常在特定分鐘數內顯現，N 應該略大於這個窗口才有意義，否則等於白白犧牲時效性卻換不到額外預測力。

### 3.4 問題：Jetson 邊緣加速的套件生態斷層與系統限制

**技術原理 — 為什麼 Jetson 上裝不到官方 onnxruntime-gpu**：PyPI（Python 官方套件庫）上的 `onnxruntime-gpu` 只提供 x86_64 架構的預編譯二進位檔（wheel），Jetson 屬於 ARM64（aarch64）架構且搭載特定的 CUDA 運算能力版本（Orin 系列為 sm_87），這個組合的使用者規模遠小於 x86 伺服器市場，NVIDIA 並未透過標準 PyPI 通路發布對應版本，直接 `pip install onnxruntime-gpu` 在 Jetson 上完全裝不起來。

**已驗證的解決方案**：改用容器化分發——`dusty-nv/jetson-containers` 專案針對每個 JetPack/L4T 版本組合，預先編譯好完整環境（含正確版本的 CUDA、cuDNN、TensorRT、onnxruntime）並封裝成 Docker 映像，直接下載對應版本的映像即可繞過從源碼編譯的複雜度。已在 Jetson 上實測 `dustynv/onnxruntime:r36.2.0`（約 13GB），容器內確認 `TensorrtExecutionProvider`／`CUDAExecutionProvider` 皆正常可用。

**技術原理 — 額外發現的網路限制**：Docker 預設的 bridge 網路模式，需要透過 iptables 的 `raw` 表格設定封包過濾規則（`DOCKER-USER` 鏈的直通過濾機制）。Jetson 這顆客製化 kernel（`5.15.136-tegra`）並未編譯 `iptable_raw` 這個核心模組，導致容器網路初始化失敗。解法是啟動容器時加上 `--network host`，讓容器直接共用主機的網路命名空間，跳過 Docker 自建的 bridge 網路與相關 iptables 規則，此法已驗證有效。
