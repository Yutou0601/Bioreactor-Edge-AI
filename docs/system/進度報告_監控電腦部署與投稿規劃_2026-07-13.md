## 1. 監控電腦開發環境建置與問題排除

金工監控電腦是全新設置的環境，過程中排除了幾個會直接卡住整條部署流程的問題，記錄下來避免下次重踩：

| 問題 | 原因 | 解法 |
|---|---|---|
| `npm run dev` 完全跑不動 | 這台電腦原本沒裝 Node.js/npm | 用 winget 安裝 Node.js LTS，並提醒安裝後**要重開終端機**讓 PATH 生效 |
| PowerShell 執行 `npm` 系列指令報 `running scripts is disabled` | 預設 Execution Policy 擋住 npm 的 `.ps1` shim | `Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned -Force`（僅影響目前使用者） |
| `python main.py` 報 `ModuleNotFoundError: No module named 'paho'` | `requirements.txt` 沒有列全，`paho-mqtt`／`pyserial`／`requests` 都缺漏（`requests` 是 `sensor_simulator.py` 早就在用但沒被列進需求檔的既有問題） | 補齊 `requirements.txt`，重新 `pip install -r requirements.txt` |
| 後端啟動時在例外處理本身又噴 `UnicodeEncodeError` 而整個服務啟動失敗 | Windows 主控台/被重導向的輸出預設用系統 codepage（如 cp1252），無法編碼程式裡的中文 `print` 訊息（`[AI 核心]`、`[MQTT]`、`[USB]` 等） | 在 `main.py` 開頭強制 `sys.stdout`/`sys.stderr` 走 UTF-8。這是**任何非互動式啟動情境**（背景執行、服務排程、log 導向檔案）都會踩到的根本問題，不是單一次意外 |
| `pip`/`python` 灌好後指令找不到 | 同樣是 PATH 沒刷新 | 重開終端機視窗即可 |

**Why 這值得記錄**：這些問題不是這台電腦特有的，是「全新 Windows 環境 + 中文訊息」這個組合必然會踩到的坑，尤其 UTF-8 編碼那個問題如果沒修，未來只要用排程器或背景方式啟動服務就會炸，過去可能被誤判為「服務不穩定」。

## 2. 前後端環境切換機制

`web_frontend/src/services/apiClient.js` 原本把後端 API 位址寫死成 Jetson 的固定 IP（`192.168.55.1`），改用 Vite 環境變數區分：

- `.env.development` → `localhost:8000/api`（本機用 `npm run dev` 開發測試用）
- `.env.production` → `192.168.55.1:8000/api`（監控電腦 `npm run build` 正式部署用，畫面顯示的是 Jetson 算出來的即時資料）

已驗證：`npm run dev` 走 localhost、`npm run build` 產出的 bundle 內確實打包進 Jetson IP，兩邊不會混淆，之後不用再手動改程式碼切換環境。

另外把 `MonitorView.vue` 裡輪詢間隔從測試用的 5 秒改回設計值 60 秒（USB 感測器本來就是每分鐘一筆，5 秒是先前測試殘留、忘記改回來的設定）。

## 3. 監控電腦部署補齊

- **前端部署步驟**已補進 [`金工電腦部署清單_2026-07-13.md`](金工電腦部署清單_2026-07-13.md)：安裝 Node.js → `npm install` → `npm run build`（自動打包連 Jetson 的設定）→ `npm run preview` 顯示畫面。
- **新增 `edge_backend/start_backend.bat`**：雙擊即可啟動 venv + `python main.py`，venv 不存在時會印出建立步驟並暫停視窗（不會一閃而過看不到錯誤），`main.py` 結束或當掉時也會暫停，方便非工程背景的人在現場操作、出狀況時也看得到訊息。
- **新增 `edge_backend/batch_import_csv.py`**：監控電腦上的歷史每日備份 CSV（`C:\Users\BTP\Desktop\data\BTP_Sensor_log-YYYY-MM-DD.csv`）原本要在網頁上一個一個手動選檔匯入，寫了一支腳本指向整個資料夾、逐檔呼叫既有的 `/import_csv` API，沿用該端點本來就有的去重邏輯（已存在的 timestamp 會自動略過），可以重複執行不會匯入重複資料。

## 4. Jetson 連網與三方 Git 同步流程

- Jetson 原本只能靠 Type-C 接電腦時走 USB 網路共享（IP 固定 `192.168.55.1`），已改連上現場 WiFi（`nmcli` 一行式 `connect` 指令在這台的 NetworkManager 版本上有相容性問題，改用 `connection add` → `modify` → `up` 三段式指令成功連上），現在 Jetson 拔掉 Type-C 也能保有網路連線（IP 會變成 WiFi 分配的，需另外查）。
- 確立三方同步流程：**本機開發 → `git push` → 監控電腦／Jetson 各自 `git pull`**。Jetson 端 `git push` 目前因 SSH 非互動式連線缺憑證會失敗，但這條流程只需要 Jetson `pull`，不影響。
- 今天已推送 3 個 commit 到 `main`：開發環境修復（UTF-8、缺依賴、環境變數）、文件補充（技術報告詳解、部署清單、會議筆記）、`start_backend.bat`。

## 5. 即時運算架構規劃：監控電腦感測 → Jetson 運算 → MQTT → 前端顯示

討論後確認的架構方向：**監控電腦負責收感測器資料與跑前端顯示畫面，實際運算（LSTM 推論）交給 Jetson**，Jetson 算完的結果透過 MQTT 發布，前端訂閱顯示。

盤點現有程式碼後發現**這個架構已經寫了一大半，只是中間缺一段轉發**：

- `core/mqtt_client.py` 已設計成跑在 Jetson 上（`BROKER_IP = "localhost"` 並註明廣播器就裝在 Jetson），訂閱 `reactor/01/sensors`、收到資料就呼叫 `get_pressure_prediction()` 推論、發布結果到 `reactor/01/prediction`。
- `MonitorView.vue` 前端已經訂閱 `reactor/01/prediction`，會自動更新畫面。

**缺口**：實體 USB 感測器目前只接在監控電腦上，但 `usb_receiver.py` 收到資料後只寫本機資料庫和 CSV，**沒有自動轉發到 MQTT**（目前只有前端手動點「發布」按鈕才會單筆送出）。要打通整條鏈，需要：

1. 確認 Jetson 上是否已安裝並啟動 MQTT broker（例如 Mosquitto）——**這是待確認事項，目前還沒有答案**，是能不能繼續往下做的前提。
2. 修改 `usb_receiver.py`，收到每筆感測器資料後自動 publish 到 Jetson 的 broker（`reactor/01/sensors`），取代目前「只有手動點擊才單筆發送」的行為。
