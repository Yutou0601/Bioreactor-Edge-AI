# 生物反應器監測系統：重構架構

**2026-09-01**　目標讀者：MIRDC 研究員、洪博、開發者

**前提**：Jetson Orin Nano 退場；前後端都跑在**同一台監控電腦**（Windows, 4 GB）；
要做成**可更新、可擴充的模組**。

---

## 0. 核心矛盾與解法

「可擴充」和「60 MB」天生對立——每加一個分析模組就多一批 import。
`torch` 496 MB、`xgboost` 97 MB、`pandas` 62 MB，兩三個模組就把預算吃光。

**解法：模組不進同一個行程。**

> 常駐的核心只做「絕不能漏資料」的事，永遠只有 numpy。
> 分析模組是**獨立的短命行程**：跑三十秒、寫回 SQLite、結束。
> 一個跑完才跑下一個。

峰值記憶體因此變成**排程問題**，不是架構問題。4 GB 的機器容得下一個
暫時佔 200 MB 的行程；容不下的是**永遠常駐**的 330 MB。

## 3. 新架構：一台機器，一個常駐行程，N 個短命模組

```
監控電腦（唯一一台）
┌───────────────────────────────────────────────────────────┐
│ ① 常駐核心   uvicorn 一個行程   目標 < 60 MB               │
│                                                            │
│   序列埠 / CSV 監看                                        │
│        ↓                                                   │
│   追加式原始日誌（一天一檔，永不覆寫）                     │
│        ↓                                                   │
│   SQLite: sample 表                                        │
│        ↓                                                   │
│   補氣切段 → 曲率預篩 → profiled 最小平方 → 套校準常數     │
│        ↓                                                   │
│   SQLite: cycle 表                                         │
│        ↓                                                   │
│   FastAPI：唯讀 API ＋ 直接供應前端 dist/（不必第二個伺服器）│
│        ＋ 模組排程器（只負責啟動子行程，從不 import 模組）  │
│                                                            │
│   相依：numpy, fastapi, uvicorn, pydantic, pyserial, sqlite3│
└───────────────────────────────────────────────────────────┘
        │ 啟動子行程（一次一個，有逾時、有鎖）
        ↓
┌───────────────────────────────────────────────────────────┐
│ ② 模組   各自獨立的短命行程   相依不限                     │
│                                                            │
│   modules/ch4_attribution/    xgboost                      │
│   modules/covariate/          pandas                       │
│   modules/greybox/            pandas, scipy                │
│   modules/calibration/        numpy（Algorithm 2 / 3）      │
│   modules/<你之後要加的>/                                   │
│                                                            │
│   讀 SQLite → 算 → 寫回自己的結果表 → 結束                 │
└───────────────────────────────────────────────────────────┘
```

**核心從不 import 模組的程式碼。**它只做一件事：在該跑的時候
`subprocess.run([python, "modules/X/run.py"])`。

## 4. 模組契約

每個模組是一個資料夾，兩個檔案：

```
modules/ch4_attribution/
  module.json
  run.py
```

```json
{
  "name":     "ch4_attribution",
  "version":  "1.2.0",
  "title":    "CH4 特徵歸因",
  "trigger":  { "type": "schedule", "every_minutes": 60 },
  "reads":    ["sample", "cycle"],
  "writes":   "mod_ch4_attribution",
  "entry":    "run.py",
  "timeout_s": 300,
  "requires": ["pandas>=2.2", "xgboost>=2.0"]
}
```

`run.py` 的合約很窄：

```python
# 收到一個參數：SQLite 路徑。
# 讀 reads 列的表，寫 writes 那一張表，然後結束。
# 不得長駐、不得寫別人的表、不得依賴核心的任何模組。
```

### 4.1 為什麼這樣就「可更新、可擴充」

| 需求 | 做法 |
|---|---|
| 新增分析 | 丟一個資料夾進 `modules/`。**核心一行都不用改。** |
| 更新分析 | 換掉那個資料夾。核心不動、不必重開。 |
| 移除分析 | 刪資料夾。 |
| 某模組壞掉 | 子行程失敗 + 逾時，**記錄器照跑**。不會拖垮資料收集。 |
| 相依衝突 | 模組各自宣告 `requires`；核心永遠只有 numpy。 |
| 版本追溯 | 結果表帶 `module_version` 欄。 |

⚠ **關鍵是那條「核心從不 import 模組」的紅線。**一旦為了方便在核心
`import` 了某個模組的函式，整個記憶體隔離就失效了，而且會在幾個月後
悄悄復發——現行 `routes.py` 就是這樣長出 torch 的。

### 4.2 前端也要能擴充，而且不必重新 build

模組把結果寫進 `mod_*` 表；前端有**一個泛用的模組頁**：
向 `/api/modules` 要清單，向 `/api/modules/{name}/result` 要資料，
用 `module.json` 裡的 `title` 當標題，資料是時間序列就畫線圖、
是表格就列表格。

**新增模組不必改前端、不必重新 build。**

## 5. 研討會的方法怎麼落地

論文的三個演算法**不是同一類東西**，這正是分層的依據。

### 5.1 Algorithm 1 → 核心（①）

每次補氣結束，對剛結束那段跑一次：

```
c ← (y(0) − y(T/2)) / (y(0) − y(T))
if c < 0.45: 捨棄，不估計
for k in K (150 點):
    D(k) ← [exp(−k·t), t, 1]
    β(k) ← 最小平方解（3×3）
    S(k) ← 殘差平方和
k̂ ← argmin S(k)
r̂_b ← −β₂(k̂)
r_b ← r̂_b × (1 − 0.048)      # 校準常數，來自模組
```

**只要 numpy。** 150 次 3×3 解，約幾百次浮點運算。論文正文即載明
「both run in NumPy alone, within the 60 MB budget of the monitoring
computer」。一整批 207 段跑完不到一秒。

### 5.2 Algorithm 2、3 → 模組（②）

模擬密集（25 次重複 × 207 段 × β 網格；41 次虛無抽樣），但**產出只有
幾個常數**：

```json
{
  "calibrated_at": "2026-08-24",
  "n_cycles": 207,
  "correction": -0.048,
  "rate": 0.0125,
  "ci95": [0.0112, 0.0139],
  "compatible_beta": [0.15, 0.80],
  "null_p": 0.024
}
```

核心讀這個檔、乘一個數字。**校準的計算永遠不進常駐行程。**

### 5.3 為什麼 Jetson 退場後這個分法更重要

LSTM 原本靠 Jetson 的 GPU。現在沒有 GPU，等於在 4 GB 的 Windows 機器上
用 496 MB 的框架換一個推論。

而論文的估計器**不是機器學習**：閉式最小平方、沒有模型檔、沒有框架、
沒有 GPU 需求，而且 k 是物理弛豫、r_b 是生物移除速率，各有物理意義，
不是黑箱預測值。

## 6. 資料表

```sql
-- 原始樣本：只追加，不更新。永遠是最後的真相來源。
CREATE TABLE sample (
  ts        TEXT PRIMARY KEY,      -- ISO8601
  pressure  REAL, orp REAL, ph REAL, temp REAL
);

-- 循環：補氣切出來的一段，估計結果一併存。
CREATE TABLE cycle (
  id          INTEGER PRIMARY KEY,
  run_id      INTEGER,
  ts_start    TEXT, ts_end TEXT,
  n_samples   INTEGER,
  duration_hr REAL,
  amplitude   REAL,        -- y(0) − y(T)
  curvature   REAL,        -- 預篩用的 c
  screened    INTEGER,     -- 是否通過 c >= 0.45
  k_hat       REAL,
  rb_hat      REAL,        -- 未校準
  rb          REAL,        -- 已套用校準常數
  resid_sd    REAL,
  calib_ver   TEXT         -- 用的是哪一版 calibration.json
);

-- 模組執行紀錄：哪個模組、什麼時候跑、成不成功。
CREATE TABLE module_run (
  id        INTEGER PRIMARY KEY,
  name      TEXT, version TEXT,
  started   TEXT, finished TEXT,
  exit_code INTEGER,
  log       TEXT
);

-- 模組結果表由各模組自建，一律以 mod_ 為前綴，且帶 module_version。
```

`calib_ver` 是關鍵：**校準常數換版時，舊資料仍能追溯它當初用的是哪一版。**

## 7b. 實驗排程（2026-09-02 新增）

### 先界定：這套系統只讀不控

`usb_receiver.py` 只從序列埠**讀**，全專案沒有任何 `.write()`。
所以**「自動停止」只是自動結束紀錄並計算結果，不會關閥、不會停反應器**。
現場仍必須有人去實際排氣。這句話寫死在 `/api/experiment/scheduler` 的
回傳裡，介面必須顯示——否則有人會以為排好時間就不用到場。

### 在此之前的狀態

`scheduled_start` 與 `target_hours` 早就存在，但**只是被存起來顯示**：
前者在按「開始」時被拿來當記錄的起始時刻，後者只用來顯示進度條
`elapsed / target`。沒有任何東西去執行它們——「排定開始時間」實際上
仍要人記得去按。`core/` 與 `main.py` 全域搜尋不到任何排程器。

### 三個時間欄位

| 欄位 | 意義 | 不填時 |
|---|---|---|
| `scheduled_start` | 到點自動開始（需勾 `auto_start`） | 維持手動 |
| `target_hours`（預設 48） | 開始後多久自動結束（需勾 `auto_stop`） | 只顯示進度 |
| `scheduled_end` | 絕對結束時刻，**優先於** `target_hours` | 用 `target_hours` |

`scheduled_end` 優先，是因為指定絕對時刻比「開始後 N 小時」明確，
尤其在 `start_time` 事後被人工修正過的時候。

### 自動結束只有兩個條件

1. 到達 `scheduled_end`
2. `start_time + target_hours` 已過

⚠ **資料中斷不列入。** 記錄程式掛掉、感測器脫落都會造成資料斷，但那不
代表實驗結束——自動結束會把一個不完整的批次標成「完成」並算出錯的結果。
資料中斷只在 `get_live_status` 的 `staleness_min` 示警，不動狀態。

### 三個容易做錯的地方

**① 結束時刻要記「應結束時刻」，不是「排程器發現的時刻」。**
後端若停機 5 小時再開，批次仍結束在它該結束的時間；否則量測結果的時間窗
會比設計多出停機那段。`system_test.py` 第 8 組有這一項的守門。

**② 自動結束不填手動峰值。** 沒有人在現場觀測，硬填等於捏造數字。
peaks 留空、退回自動抓取，並記 `ended_by="auto"`。⚠ 感測器 1 筆/分鐘常
錯過排氣瞬間的 CH4 峰，所以前端對 `ended_by === 'auto'` 的批次顯示
「⚠ 排氣時刻待確認」；人工 PATCH `end_time` 之後標記自動解除。

**③ 預設必須關閉。** `auto_start` / `auto_stop` 兩個旗標不勾就完全維持
原本的手動流程。既有批次的 JSON 裡沒有這兩個欄位，`.get()` 取到 `None`
＝關閉。system_test 第 8 組把「沒勾旗標者不被排程動到」列為守門項——
只要有人把預設改成開啟，既有的手動批次就會在下次啟動時被悄悄接管。

### 排氣提醒

距應結束剩 `VENT_REMIND_HOURS`（0.5 hr）時，`get_live_status` 回傳
`vent_reminder: true`，前端跳橘色提示。⚠ **就算開了 `auto_stop` 這個提醒
仍然要出現**——它提醒的是「該去現場」而不是「該按按鈕」。
提醒用牆上時鐘算，不用最後一筆資料的時間：記錄若中斷，`elapsed_hours`
會停住，但實驗仍在跑，提醒不能跟著停。

### 實作

`edge_backend/core/scheduler.py`，daemon 執行緒每 30 秒一輪，由
`main.py` 的 lifespan 啟動。只用 `threading` + `datetime`，不引入
APScheduler 之類的套件（60 MB 預算）。判定邏輯抽成純函式
`pending_actions(runs, now)`，可以餵任意 `now` 進去測，不必等 30 秒
也不必真的動到批次。

| 端點 | 用途 |
|---|---|
| `GET /api/experiment/scheduler` | 活著沒、下一件事、最近做過什麼 |
| `POST /api/experiment/scheduler/tick` | 立刻檢查一輪，不必等 30 秒 |

⚠ `due_time()` 的定義放在 `experiment_store` 而不是 `scheduler`：
scheduler 匯入 store，反向會循環匯入。

### ✅ `sample` 表（2026-09-10 已建立）

`core/sample_store.py`。除了「重啟不掉資料」之外，它解掉的是一個會隨時間
惡化、而且不會當場報錯的問題——實測每筆記錄在記憶體佔 **517 bytes**：

| 保留量 | 筆數 | 記憶體 |
|---|---:|---:|
| 7 天 | 10,080 | 5.0 MB ✓ |
| 30 天 | 43,200 | 21.3 MB ✗ |
| 1 年 | 525,600 | **259.1 MB** ✗✗ |

所以分工是：**SQLite 存完整歷史，記憶體只留有界的最近視窗**（預設 20000 筆）。
要看更早的資料查 `sample_store.load_window()` 或 `GET /api/samples/window`。

⚠ 還原用「最近 N 筆」而不是「最近 N 天」：現場會匯入**歷史**批次的 CSV 再
分析，用牆上時鐘算天數的話那些資料重啟後會全部落在視窗外、等於憑空消失。

⚠ schema 比 §6 多七欄（orp_raw / orp_cleaned / is_anomaly / mixer_pressure /
co2_pct / ch4_pct / note）。§6 只列五欄，但那七欄都有使用端；只存五欄的話
重啟還原後它們會靜默變成預設值，圖看起來正常但內容是假的。

模組目前仍走 `input.json` 快照（`compute_cycles()` 讀的還是記憶體）。要讓
模組直接讀 `sample` 表，把 `module.json` 的 `input` 拿掉、改在 `run.py` 裡
查表即可，核心不用動。
