# CH4 每分鐘連續記錄：Pipeline 改動與實驗紀要

**整理日期**：2026-07-11
**用途**：2026-07-13（一）與洪博討論用素材
**投稿目標**：ACM ICEA 2026（智慧運算暨新興應用國際研討會，雲端/邊緣運算 track），截稿 2026-08-31

---

## 1. 研究背景與動機

現有系統以 ORP 訊號預測 CH4，離線分析（`ch4_peak_analysis.py`）過去只取「每個排氣週期一個 CH4 峰值」當標籤，樣本量僅 **n=6**，LOO-CV 統計可信度低。本次改動的核心目標：把 CH4 從「每週期一個標量」升級為「每分鐘連續記錄」，大幅擴增樣本數，並重新檢驗 ORP 相位動態對 CH4 的解釋力。

## 2. 資料

探索專案時發現 `edge_backend/data/` 已有真實資料：**2026-02-10 ～ 2026-03-27，共 46 天、62,640 筆逐分鐘紀錄**（非合成資料）。所有本次實驗結果均基於這批真實資料，非模擬數據。

- 目前系統偵測到 **6 個完整排氣週期**（`scipy.find_peaks` 於 CH4 訊號上偵測），與既有文件描述一致。
- Jetson 上目前**沒有** `usb_receiver.py`／`main.py` 在執行中（今天 SSH 確認），代表這批資料是先前某次運行留下的，非即時進行中。

## 3. Pipeline 改動與修復的既有問題

| 項目 | 內容 |
|---|---|
| CSV 格式相容性 | `usb_receiver.py` 實際寫出的每日備份格式（12欄、有標題）與 `loader.py` 原本預期的舊格式（14欄、無標題）完全不相容，導致正式收集的資料原本無法餵進分析腳本。已修好，`loader.py` 現在自動偵測並相容兩種格式。 |
| `/import_csv` 網頁匯入 | 同樣的格式問題也讓網頁版「匯入每日備份 CSV」功能完全失效（每筆都被跳過）。已修好並驗證（含去重測試）。 |
| `python-multipart` 缺失 | `requirements.txt` 漏了這個套件，缺了它 FastAPI 後端連啟動都會直接失敗（`/import_csv` 用到 `File()`）。已補上，這是全系統等級的阻斷性問題。 |
| CSV `note` 欄位 bug | 空白 note 欄位是 `NaN` 而非空字串，原本的 `or` 判斷邏輯抓不到，已修正。 |

## 4. 方法論：Cycle-level baseline vs Minute-level

### 4.1 Cycle-level（既有方法，作為 baseline 保留）
- 11 個週期級特徵（`cycle_length_min`、`phase2_duration_min` 等），GA + Ridge/RF，LOO-CV。
- **結果**：n=6，Ridge LOO-CV RMSE **3.13%**，RF LOO-CV RMSE 10.17%。
- GA 選中特徵：`cycle_length_min, phase2_duration_min, phase2_fraction, phase3_onset_fraction, pressure_mean`
- RF 最重要特徵：`ph_mean`（重要性 0.2660）
- 與 CH4 峰值相關係數最高：`phase2_duration_min`（r=+0.873）、`cycle_length_min`（r=+0.863）、`phase3_onset_fraction`（r=-0.800）
- CH4 峰值範圍：33.9% ~ 66.2%

### 4.2 Minute-level（新方法）
- 逐分鐘特徵：ORP EMA/斜率/MACD（**依連續區段而非週期計算**，避免週期邊界 EMA 冷啟動失真）、相位標籤、週期內時間位置、壓力/pH/混合槽壓力/CO2。
- 交叉驗證改用 **GroupKFold**（依週期分組，6折）+ **時序 holdout**（早期資料訓練、晚期資料驗證），取代大樣本下不再適用、且有已知分布偏誤疑慮的 LOO-CV。
- **結果**：n=58,490（樣本數提升近萬倍），GA 選中特徵：`orp_slope, orp_macd, elapsed_frac_in_cycle, ph, mixer_pressure, co2_pct`
  - Ridge GroupKFold RMSE：**4.26%**
  - RF GroupKFold RMSE：**2.28%**
  - RF 時序 holdout RMSE：**1.72%**

## 5. 消融實驗設計與結果

為了拆解「哪些訊號真的在解釋 CH4，哪些只是巧合的高相關」，設計了 5 組消融實驗（均在同一批真實資料上跑）：

| 消融 | 特徵組合 | 要回答的問題 | 樣本數 | Ridge(GK) | RF(GK) | RF(時序) |
|---|---|---|---|---|---|---|
| **main（基準）** | 完整每分鐘特徵集 | — | 58,490 | 4.26% | 2.28% | 1.72% |
| no_time | 排除週期進度特徵 | ORP/操作參數在不知道「現在第幾分鐘」時是否仍有預測力 | 58,490 | 5.96% | 2.98% | 1.86% |
| orp_only | 僅 ORP 衍生特徵（EMA/slope/MACD/phase_label） | ORP 本身能解釋多少 CH4 變異 | 58,490 | 6.78% | 7.24% | 7.95% |
| non_orp_baseline | 排除 ORP 與時間特徵，僅壓力/pH/混合槽壓力/CO2 | ORP 感測器是否真的必要 | 58,490 | 5.99% | 2.93% | 1.99% |
| minimal_sensor | ORP + pH（最小感測器組合） | 邊緣部署精簡感測器成本論述 | 58,490 | 6.78% | 7.24% | 7.95% |
| with_lag | 額外納入 CH4 落後值 | 模型能否偷看答案（上界對照） | 57,969 | 0.19% | 0.20% | 0.18% |

## 6. 關鍵發現與需要誠實討論的地方

1. **樣本量問題已解決**：從 n=6 到 n=58,490，統計可信度大幅提升，這是本次改動最直接、最沒有爭議的貢獻。
2. **`orp_only` 與 `minimal_sensor` 結果完全相同**（GA 都自動排除了 `ph`）：純 ORP 特徵 RF RMSE 為 7.24%，明顯弱於主結果（2.28%）。
3. **⚠️ 核心論點需要更精確的措辭，而且極可能受樣本數限制影響**：整體 pooled RMSE 比較（`non_orp_baseline` 2.93% vs 主結果 2.28%）看起來差距不大，但**逐折（per-fold）拆開來看是另一回事**——6 折中有 5 折顯示「有 ORP」表現更好，配對差異平均 +0.53 個百分點；然而 `main` 模型自己的逐折 RMSE 就從 1.49% 跳到 3.03%（近兩倍），標準差 0.58，跟「有無 ORP」的平均差異是同一個數量級。也就是說：**目前 n=6 個週期的統計檢定力太低，還無法可靠區分「ORP 有中等程度的邊際貢獻」跟「ORP 貢獻確實很小」——點估計偏向後者，但逐折資料其實比較支持前者，兩者信賴區間顯然重疊**。這不是靠更換分析方法能解決的，需要更多獨立週期（新硬體每分鐘排氣偵測上線後，累積到 20-30 個週期以上）才能讓這個估計收斂。
4. **時間特徵確實有實質貢獻但非全部**：`no_time` 消融後 RMSE 只從 2.28% 小幅上升到 2.98%，顯示 ORP + 操作參數確實有一部分獨立於「週期進度」的解釋力，不是模型單純在學時間趨勢——這點對論文是正面支持。
5. **`with_lag` 驗證方法論嚴謹度**：CH4 自身落後值幾乎完美預測下一分鐘（RMSE→0.19%），證實 CH4 高度自相關；主結果刻意不用這個特徵，避免論文被質疑「模型只是在抄答案」。
6. 建議論文措辭從「ORP 相位動態決定 CH4」調整為更精確的「ORP 相位動態提供獨立於操作參數與週期進度的額外解釋力，但目前樣本數（n=6 週期）尚不足以精確量化其效應大小，需累積更多獨立週期後進一步驗證」，誠實標註統計檢定力的限制，會比硬下結論更禁得起審稿人檢驗。

## 7. 技術可行性初探（回應「要不要做 Bi-LSTM/PINN/雙環境部署」的提案）

背景：另一份 AI 生成的研究計畫書提議把演算法升級為 Bi-LSTM/PINN，並建置 x86 監控電腦 + Jetson 雙環境（Docker + ONNX Runtime + TensorRT）進行影子部署驗證，時程規劃 5-6 個月。**但實際截稿日是 2026-08-31，只剩約 7 週**，故針對此提案做了初步可行性驗證：

### 7.1 ONNX 匯出（在 x86 開發機上測試）
- 把現有 `ReactorLSTM` 匯出為 ONNX，PyTorch 與 ONNX Runtime 輸出誤差 1.49×10⁻⁸（數值等價），動態 batch size 驗證通過。
- 過程中連續踩到 3 個環境地雷（缺 `onnx`/`onnxruntime`/`onnxscript`，opset 版本不符），但均可快速排除。已寫成可重用腳本 `edge_backend/export_onnx.py`。
- **結論**：x86 端匯出機制可行，但這只驗證了「隨機權重、CPU 推論」這條路，Jetson 端與真實訓練權重仍是未知數。

### 7.2 Jetson 現況（SSH 連線確認）
- JetPack 版本：L4T R36.3.0（JetPack 6.x）
- 已裝好 NVIDIA 官方 CUDA 版 PyTorch（`torch 2.4.0a0+...nv24.5`）、numpy/pandas/scikit-learn
- **尚未安裝 onnx/onnxruntime**（Jetson 上不能直接 `pip install onnxruntime`，需要 NVIDIA 對應 JetPack 版本的專用 wheel，這是下一個待驗證的地雷）
- Docker：**專案目前完全沒有任何 Dockerfile**，多架構容器化是從零開始

### 7.3 時程風險評估
- 影子部署測試需要 **14 個日曆天**，無法用加班壓縮。若要在 8/31 前留出分析寫稿時間，最晚必須在 8/17 前啟動測試。
- 也就是說，Docker + ONNX（Jetson端）+ TensorRT 這整條基礎設施，必須在 7/13-8/17 約 5 週內從零建置到能穩定跑 14 天不出包。
- **PINN 部分有方法論疑慮**：Modified Gompertz 模型是批次式沼氣測試的經典模型，本反應器是連續進料運作，兩者數學前提不完全對齊，需要生化背景判斷是否適用——這不是工程問題，需要洪博確認。
